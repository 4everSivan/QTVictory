## 1. 简介

QTVictory 专为量化交易开发者、策略研究员以及量化智能体（AI Agent）打造。它通过轮询公开市场的真实行情（腾讯/东方财富接口），并在内存中以严格的 A 股交易制度模拟撮合，构筑起一个**低成本、高保真、零外部依赖**的实时前向仿真（Paper Trading）沙盒。

在 QTVictory 中：
- **交易员（Trader）即策略实例**：每个交易员代表一个被测策略实例（`strategy` 模式）或手动对照基准（`manual` 模式），拥有独立的虚拟资产账户、持仓账本与交易流水；
- **观察员（Observer）全权审计**：系统设立唯一的观察员角色，作为全局管理员监控所有交易员的运行状态，但不持有资金、不参与交易、不下单，保证多策略对比时权限与绩效评估的绝对公正；
- **API-First 程序化集成**：控制台 UI 仅是系统的标准客户端之一，系统全部核心能力（行情订阅、下单撤单、交易计划、资产统计、数据导出）均开放为规范的 RESTful API 与 WebSocket 事件流，天然支持外部 Python 脚本、量化框架及 AI Agent 程序化调用。

## 2. 目标

### 2.1 解决的核心痛点
在传统的量化策略研发中，从“历史回测”到“实盘交易”之间存在巨大的鸿沟，通常面临以下失真：
1. **滑点模型失真**：多数模拟系统采用固定的百分比滑点或以现价 100% 立即成交，忽略了实际盘口深度与成交量限制；
2. **制度规则失真**：忽视 A 股特有的 T+1 制度、连续竞价价格笼子（±2%）、涨跌停不可买入/卖出、科创板/主板申报单位差异等微观制度；
3. **多策略隔离困难**：缺乏统一的实例管理沙盒，多策略并行对比时资金口径与基准参照往往不一致；
4. **系统复杂度过重**：传统交易系统通常重度依赖 Redis、Kafka、MySQL 等外部服务集群，单机开发、测试与沙盒验证运维成本过高。

### 2.2 核心设计目标
- **制度级真实仿真**：以买卖五档盘口驱动撮合，引入真实成交量（单 tick ≤ 25% 真实成交量）与流动性约束，真实还原部分成交（Partial Fill）、价格笼子申报拦截与滑点损耗；
- **同源竞逐对比**：支持任意数量的交易员实例在同一行情源下并行运行，统一以沪深300（sh000300）为绩效基准，支持夏普比率、最大回撤、超额收益同口径评估；
- **机器与智能体友好**：无私有前端逻辑，所有状态校验下沉至领域层；提供幂等控制（`Idempotency-Key`）、令牌桶限流与全量观察员审计日志；
- **单机轻量自愈**：基于 Python 异步生态与 SQLite (WAL) 构建，单进程运行、零外部依赖；内置行情三级降级自愈链，弱网或源端故障时自动保障撮合平稳运转。

### 3.1 系统全景与五大支柱飞轮

QTVictory 致力于打通“**信息感知 → 策略模拟演练 → 周期自适应奖励 → 深度归因调优 → 实盘安全投产**”的完整闭环，以“高保真模拟底座”为起点，逐步演进为自适应量化交易操作系统。五大核心支柱协同构筑起自我进化的飞轮机制：

1. **支柱 1 · 基础模拟盘底座 (Paper Trading Platform)**【✅ Phase 1 现行交付基线】：提供 A 股制度级真实撮合（五档买卖盘、价格笼子、成交量限制、T+1）、行情三级降级自愈链、观察员审计体系以及 API-First / WebSocket / 极简 Web 控制台；
2. **支柱 2 · 周期自适应奖励系统 (Adaptive Reward Engine)**【📋 Phase 2 规划】：解耦“微观执行考核（秒级滑点/冲击）”与“宏观策略考核（短线胜率期望 / 波段盈亏比 / 长线超额收益）”，引入小样本置信度防过拟合检验；
3. **支柱 3 · 策略分析与回测平台 (Analytics & Backtest Hub)**【📋 Phase 3 规划】：100% 复用纯函数撮合内核进行高速历史回测，聚焦实现偏差归因（Implementation Shortfall）与参数稳健高原（Robust Plateau）寻优；
4. **支柱 4 · 金融信息感知中枢 (Intelligence Hub)**【📋 Phase 4 规划】：信息不做涨跌黑盒预测，而是用于“负向排雷门禁（黑天鹅硬风控）”与“宏观市场状态识别（Regime Detection）”，动态指导策略启停；
5. **支柱 5 · 实盘操作系统与执行中枢 (Live Trading OS)**【🔭 Phase 5 远期愿景】：统一抽象双轨路由网关（`mode: "sim"` 与 `mode: "live"` 零改动平滑切换）、对接券商量化接口、毫秒级异步对账状态机、TWAP/VWAP 算法拆单与独立物理硬熔断（Hard Kill-Switch）。

### 3.3 各层核心机制设计

1. **核心领域内核 (Domain Kernel —— 无 I/O 纯函数)**：
   - **`MatchingEngine` 撮合引擎**：完全剥离网络与持久化副作用，接收 `(订单, 盘口快照, 历史成交基数, 规则配置)` 输出 `(成交结果, 资产变更)`。支持五档市价单（最优五档剩余撤销、对手方最优）、限价单排队撮合、单 tick 成交量约束（不超过标的增量成交量的 25%）、连续竞价有效申报范围（买入 ≤ 卖一 × 102%、卖出 ≥ 买一 × 98%）、T+1 可卖额度锁定、印花税（千 0.5 单向）与佣金（5元保底）扣减、中证登现行过户费率（十万分之一双向收取）；
   - **`PlanEngine` 计划引擎**：支持价格穿越（`price_cross`）、涨跌幅（`change_pct`）、均线交叉（`ma_cross`）、定时触发（`time`）四类触发器；策略触发后必须经受“标的池围栏 → 资金预算围栏 → 目标仓位围栏 → 单笔风控围栏”四道校验，防范失控交易；
   - **`Strategies` 策略模板库**：内置 8 类标准量化策略模板（网格、双均线、动量突破、MACD 等），作为功能验证与观察员横向评估的基准参照。

2. **服务编排层 (Application Services)**：
   - **行情服务 (`MarketService`)**：以 3 秒为基准周期轮询快照，首启引导拉取全量历史日K并支持冷热双态 bar 合成（当日热 bar ∪ 历史冷序列）；支持自然周/自然月多周期聚合（week/month 接口）、分钟线盘中增量落库与收市自动刷盘、以及腾讯 day/query 最近交易日全量分时引导；维系“动态关注集”（全体交易员持仓 ∪ 交易计划池 ∪ 沪深300指数）；
   - **四级降级链路**：优先使用腾讯行情通道（https 失败自动降级 http 兜底），源端异常时无缝切换至新浪主源档（https + Referer 防盗链透传，完整五档与累计成交量）或东财接口；当外网中断时切入内置基准锚点（Anchor），同时撮合引擎自动回退至固定滑点安全模式并在订单上逐笔标记 `fill_model=fallback`；
   - **日切与公司行动 (`SessionService`)**：每日 15:00 收盘后执行日切结算，冻结资金与股份重置，支持现金分红与送转股除权除息计算；未来日期守卫拦截日切滚雪球。

3. **表现层 (Nothing Web Console)**：
   - 基于 React 18 + Vite 构建，采用 Nothing 极简工业美学，严格贯彻“单色灰阶构筑层级、红色仅用于数据语义”的视觉哲学；
   - 摒弃厚重视图库，采用原生纯 SVG 构建多周期 K 线蜡烛图（分时/日K/周K/月K）、当日分时图与真实净值对比曲线，毫秒级响应；单副图槽位（VOL/MACD/RSI/KDJ）沉底对称，顶栏第二胶丸组（MA/EMA/BOLL）靠左紧随月K并保持 12px 舒适间距，支持多指标叠加与独立着色；
   - 支持深色（Nothing Dark）、浅色（Standard Light）与跟随系统（System）三态主题无缝切换与持久化；全界面数据强制采用等宽字（`tabular-nums`）排布；支持自选股编辑列表（名称联想添加/置顶/删除与引用码回落保留）。

## 4. 文档治理规范

QTVictory 建立了极为严格的**文档先行（Documentation-First）**与**质量防线体系**，所有贡献者与 AI Agent 必须遵守 [AGENTS.md](AGENTS.md) 协作红线与 [docs/README.md](docs/README.md) 文档规约。

### 4.1 双链路事项流转机制

项目的所有事项严格区分为“功能设计”与“缺陷修复”两条独立流水线，坚决杜绝“无设计写代码”或“无卡片修代码”：

```
                    【待办与需求缓冲池 docs/devel/todo/】
                    ├── now.md (当前版本缺陷 BG / 微调 EN 表格)
                    └── future.md (后续版本功能 FT / 技术债务 TD 表格)
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
       【缺陷修复链路 (BugFix/微调)】       【功能设计链路 (新特性/Phase立项)】
                     │                               │
                     ▼                               ▼
       docs/devel/change/               docs/devel/design/
       复制 template.md 建立 C00x 卡    编写或更新设计方案章节
       （★ 建卡即从 todo 表格中物理删除）   （★ 设计评审定稿即从 todo 移出）
                     │                               │
                     ▼                               ▼
       改代码 + 补回归测试 (pytest/vitest)  docs/devel/plan/ + task/
                     │                  新建 M / T 卡拆解开发 (Phase 2 起)
                     ▼                               │
       design/ 章节原位反向标签与回链                ▼
       (> 📌 关联变更: [C00x]...)       开发 + 测试全量通过
                     │                               │
                     ▼                               ▼
       AI 实测汇报 ──► 人工会话确认      docs/devel/report/
                     │                  新建阶段验收报告 (通过/未通过)
                     ▼                               │
       AI 代签收尾 (核验通过)                         ▼
                     │                  收口冻结 T 卡 + CHANGELOG 记账
                     └───────────────┬───────────────┘
                                     │
                                     ▼
                    全链路双向互链闭环 + 适时打 Git Tag
```

### 4.2 七大协作红线（不可绕过）

1. **变更先行卡**：Bug 修复、功能回调、参数调整或接口微调，必须先在 `docs/devel/change/` 建立 `C00x` 变更卡（填写前后对比三联表、影响面分析与 Checklist）再修改代码，严禁先斩后奏；
2. **待办缓冲池（零沉淀纪律）**：所有未入轨事项在 `docs/devel/todo/`（`now.md` / `future.md`）以表格登记。一旦事项建立 C 卡或落入设计稿，**必须立即从 todo 表格中物理删除**，`todo/` 坚决不保留 `[x]` 历史勾选项；
3. **设计方案活基线与双向回链**：`docs/devel/design/` 保持“全文自洽”。变更涉及设计规则时，必须在对应设计章节原位嵌入反向引用标签（`> 📌 **关联变更**: [C00x]...`），文档头部追加 C 编号，文末变更记录补充回链，彻底消除单向孤岛；
4. **AI 会话核验代签机制**：变更卡核验不要求人工手签，由 AI 执行自动化测试与实测后向人工汇报；人工在会话中确认无误后，由 AI 代签签署收口并记录会话确认凭证；
5. **历史版本归档库（只读封存）**：版本打出 Tag 后，该版本的 `plan/`、`task/`、`report/` 整体以及 `assessment/` 下的评分报告按 [docs/archive/README.md](docs/archive/README.md) SOP 物理迁移至 `docs/archive/<版本号>/` 只读封存；评分规则（标准与流程）及活文档（`design/`、`change/`、`todo/`、`env/`）常驻 `devel/` 持续轮转；
6. **测试环境隔离红线**：本地测试实例运行必须与生产默认完全隔离（端口强制 `8788`、数据库强制 `local/data/qtvictory_test.db`，所有测试过程产物收拢至 `local/`，严禁污染源码树）；
7. **治理流收口回调**：每次 change / design 治理链路走完（含收口、双向回写闭环、tag 打出）后，必须回调 `scripts/jev_workflow_check.py` 做治理状态自检，输出作为该链路的收口证据；自检判为“存在治理违规”时不得合入主干。

## 6. 关键设计决策

本项目核心权衡均经过严格的对抗评审定稿（详见 [02-后端设计方案 §6.13](docs/devel/design/02-后端设计方案.md#613-开放问题对抗评审进行中)）：

1. **观察员不直接交易（决议 Q1）**：系统唯一的观察员为审计者而非交易者（无账户、不下单、不入排行）；手动交易需显式创建 `manual` 模式交易员代为操作。权限边界清晰，全量动作落入审计流水；
2. **空世界初始启动（决议 Q2）**：初始启动时不预置模拟订单，定位是纯净量化底座而非商业展示软件；内置的 8 种策略模板仅作为功能验收与策略基线；
3. **撮合仿真坚持“规则级”而非“固定滑点”（决议 Q3）**：引入买卖五档盘口驱动与真实成交量约束（单实例每 tick ≤ 标的真实成交量 25%，多实例共享配额池），避免脱离真实深度的无限成交假象。固定滑点仅在行情源全断时作为兜底模式；
4. **单机默认免鉴权（决议 Q4）**：纯私人单机定位，默认只监听 `127.0.0.1` 环回接口；可通过配置环境变量 `QTV_API_KEY` 开启观察员凭证鉴权，不在本地场景引入过度复杂的 OAuth/用户系统；
5. **事件通道坚持 WS 主路 + REST 轮询兜底（决议 Q6）**：纯单机环境下，外部程序主动连接 WebSocket 最为健壮自然；不做反向 Webhook 回调，避免引入无收益的鉴权、重试与网络穿透复杂性。

## 7. 免责声明与已知边界

### 免责声明
**本项目仅供量化技术研究、算法逻辑学习与模拟测试使用，不构成任何投资建议或证券咨询。** 模拟交易中的收益率、最大回撤与胜率不代表任何实盘投资表现。投资者入市需自行承担真实市场风险。

### 已知设计边界
1. **分钟线自沉淀机制**：免费源公开接口分钟线历史深度有限且质量较低，系统不作远期历史分钟线批量回补；已支持盘中新分钟桶增量落库与停机刷盘、以及腾讯 `day/query` 最近一个交易日全量分时引导（242 点，Q8 修订）；历史分钟线自系统部署上线之日起由日切收盘任务自动逐日沉淀累积；
2. **现金分红简化税率**：系统支持现金分红与送股派息入账，但统一采用可配置的固定分红税率（默认 10% 或免税），不模拟差异化个人所得税持有期算法（>1年免税 / 1月~1年10% / <1月20%）；
3. **快照级行情频率**：基于免费公开源，行情采集为 ~3 秒快照轮询，不支持毫秒级 Level-1 / Level-2 逐笔委托数据流。
