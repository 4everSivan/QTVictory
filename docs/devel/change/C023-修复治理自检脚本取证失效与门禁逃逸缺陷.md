## 1. 变更背景与动因

C022 收口时按 AGENTS.md 红线 7 回调 `scripts/jev_workflow_check.py`，该脚本首次作为治理门禁投入实战。实战后做了一轮对抗性复查 + 本地实证，发现 16 项缺陷；16 项修完后的实跑验收又暴露 5 个新缺陷，共 21 项一次处理完。其中最严重的不是\"报错\"，而是**无声失效**——脚本会把治理违规放过去，或在违规时给出\"干净检查点\"的结论：

- **零沉淀门禁被绕过**：`docs/devel/todo/now.md` 的流转纪律段存在复合形态 `EN-0002/EN-0003 已流转至 [C002]/[C003]`，流转账本正则只捕获到 `EN-0003→C002`——EN-0002 整个从账本消失、EN-0003 还被错配。若 EN-0002 回流 todo 表，`sediment_violations` 为空，红线 7 门禁静默放行。
- **`--offline` 模式绕过代码侧硬判**：注入「状态: 核验通过（x）」后跑 `--offline`，屏幕打印「非法状态 ['C022']」但退出码仍为 0。`illegal_status/illegal_type/sediment_violations` 是纯代码判定、与 Jev 无关，offline 模式本该照样门禁。
- **错误路径自身崩溃**：`call_jev` 的 `json.loads(resp.read()...)` 与 `HTTPError` 分支内的 `exc.read()` 均无保护，实测三类异常（非 JSON 响应体 / 读体超时 / 错误分支读体失败）以 traceback + exit 1 逃逸，而 docstring 声明的契约里没有 exit 1。
- **exit 5 门禁泄漏**：`validate_response` 不校验 `confidence`/`probabilities` 类型，实测 3 种畸形形状全部"校验通过"后在打印阶段崩溃成 exit 1，正好违背它自己写下的「绝不把残缺响应当成通过」。
- **核心取证题指向不存在的字段**：`sync_complete` 指令引用 `current_state.latest_change_card`，真实字段是 `latest_verified_card`，等于让 Jev 核对一份取不到的取证对象。

另有一批低成本项：死载荷、列名定位失效、noul 极性不一致、`unmerged_cards` 判别过窄、locale 依赖、死代码、零测试覆盖等。本卡一次性全部处理，避免多轮迭代。
上述 16 项修完后的实跑验收又暴露 5 个新缺陷，同批处理：

- **阶段交叉校验误拦正常中间态**：本仓库的常态是「新变更卡待核验 + 上一卡已核验通过但尚未合入」。`cross_check` 逐事实独立设约束，这个常态同时命中两条约束，3 次实跑全部 exit 4——而 Jev 的阶段判定本身是置信 0.99 的 `等待核验`，代码侧在否定一个高置信判定。门禁反向失效：把干净检查点判成违规，运营者会学会忽略退出码。
- **低置信语义判定被当成硬判据**：合规档位低于阈值即拦，不看置信。3 次实跑该题置信 0.30/0.52/0.31，两个候选档位分布 0.44 vs 0.42 近乎平票，是模型自己都不确定的判断。AGENTS.md 明文规定这类判定「仅供参考，须人工核对采集事实后决策」，脚本却拿它硬拦。
- **noul 型答案永久误报警**：noul 型答案没有 `confidence` 字段，`None` 被当成低于阈值，三条 noul 每轮都打「⚠ 低置信」。永久噪音等于没有噪音。
- **noul 判罚与展示层自相矛盾**：门禁读 noul 概率时用裸 `p < 0.5`，完全不看展示层尊重的 `NOUL_UNCERTAIN_BAND`。实跑出现过答案行写「双向同步点已全部完成：不确定（概率接近 0.5）[P=0.36]」、结论行同时写「仍有同步点缺失（P=0.36）」并 exit 4——同一份概率在两层给出相反定性，正是本卡要消除的输出形态。
- **不确定带对模型噪声过窄**：带宽 ±0.15 的下沿是 0.35，而同一输入（干净仓库）连续 4 次实跑 P=0.33/0.36/0.37/0.42 横跨该线，其中一次落在线外直接 exit 4。干净仓库被门禁拦住一次，运营者就会开始忽略退出码；而真实违规实跑仅 P=0.06/0.09，两侧本有充足空档可切。
