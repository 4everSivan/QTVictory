# 变更与人工核验卡 (change/)

> **定位**: 解决日常 Bug 修复、功能回调、参数调整的“抗漂移与人工核验”记录目录
> **解决痛点**: 避免直接篡改已冻结的历史任务卡，为每次修改提供清晰的前后对比表与核验清单（Checklist）。

---

## 1. 为什么需要变更核验卡？

在 Phase 1 阶段性收口后，系统进入维护与渐进演进期。传统的线性任务卡（`T01–T22`）已经归档封存。

当发生以下情况时，**严禁回过头去修改旧任务卡，也不要只改代码而使文档失真**：
1. **Bug 修复 (BugFix)**：发现并修复了撮合、行情、或者前端渲染中的缺陷；
2. **功能回调 (Rollback)**：实测后发现某项设计不合理，需要回调至上一版参数或逻辑；
3. **接口/契约微调**：前后端联调时对请求参数、错误码或枚举值进行调整。

此时，只需在 `docs/devel/change/` 下新建一张变更核验卡（以 `C001`、`C002` 递增编号），记录变更原因、前后对比及人工核验清单。

---

## 2. 变更卡使用流程

```
[发现 Bug / 提出回调] 
        ↓
[从 template.md 复制新建 C00x-xxx.md]
        ↓
[填写前后对比表与 Checklist]
        ↓
[修改代码 + 补充测试用例]
        ↓
[AI 跑测试实测并在会话中汇报对齐]
        ↓
[人工确认无误 → AI 代签收尾（状态转为核验通过）]
        ↓
[代码提交并合入主干]
        ↓
[双向回写闭环：
 1. design 对应章节原位增补回链提示（> 📌 关联变更: [C00x]...）
 2. design 头部"关联变更"追加 C 编号，文末变更记录追加回链条目
 3. CHANGELOG.md 按 docs/README.md §3.3 记账并回链 C 卡，合入打 tag]
```
