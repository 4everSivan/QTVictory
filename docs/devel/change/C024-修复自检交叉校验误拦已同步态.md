## 1. 变更背景与动因

C022 收口后回填 `关联提交` hash，`unmerged_cards` 由 `['C022']` 变为空。此时联网跑 `scripts/jev_workflow_check.py` 得到 **exit 4（检测到治理违规）**：

```
· 当前阶段 (Choice)：等待双向同步 · 已核验通过但回链/CHANGELOG 未闭环  [置信 0.62]
    分布：等待双向同步 · 已核验通过但回链/CHANGELOG 未闭环 0.70，空闲 · 无进行中变更 0.27，等待合入/发布 · 已核验通过且已同步 0.02
· 双向同步点已全部完成 (Noul)：不确定（概率落入不确定带）  [P(yes)=0.44]
· 整体合规 (Choice)：整体合规，个别待办（代表值 0.90）  [置信 0.81]

检测到治理违规：阶段判定与代码事实矛盾：无未完成步骤，代码侧期望「空闲 · 无进行中变更」，实际判为「等待双向同步 · 已核验通过但回链/CHANGELOG 未闭环」
```

**逐项核查代码侧可验证事实，未发现任何真实缺口：**

| 核查项 | 结果 |
|---|---|
| 23 张变更卡的 `关联提交` hash 是否都存在于 git 历史 | 全部存在 |
| 23 张卡是否都在 CHANGELOG 有条目 | 全部有条目 |
| 带 design 链接的卡，其 C 编号是否已在对应 design 文档回链 | 22/22 全部回链 |
| C023 无 design 链接是否合法 | 合法——卡内明确声明「不改动任何设计规则，故不触发 design 双向回链」 |
| `sediment_violations` / 封存目录 | 空 / 干净 |

即**这是一个纯误拦**。Jev 自己的 compliance 判定也是「整体合规，个别待办」（置信 0.81），并未认为存在违规。

**根因**：`cross_check()` 把 `awaiting_bidirectional_sync` 的放行条件绑在 `ca["unmerged_cards"]` 非空上。但「双向同步是否闭环」是代码侧**两个方向都裁不了**的语义判断——`design/` 原位回链、头部「关联变更」追加、CHANGELOG 互链都要读正文才能确认（原注释自己也这么写）。这个条件于是造成一个反向漏洞：**当所有卡都已合入（`expected_stage()` 返回 `idle`）时，`awaiting_bidirectional_sync` 反而不被放行**，Jev 一旦对同步闭环猜疑，就被升级成 exit 4 硬违规。

**为什么必须修**：`unmerged_cards` 为空正是每次正常收口后的必经路径，也就是说这个误拦每次收口都会踩到。干净检查点被硬拦一次，运营者就会开始忽略退出码——这正是红线 7 门禁要防的失效模式，比漏拦更危险。

## 2. 规则与设计变更对照（人工核验重点）

| 维度 | 变更前（旧逻辑） | 变更后（新逻辑） | 取舍理由与影响边界 |
|---|---|---|---|
| **交叉校验放行集** | `allowed = {expected, "has_violation"}`，仅当 `unmerged_cards` 非空时才追加 `awaiting_bidirectional_sync` | `allowed = {expected, "has_violation", "awaiting_bidirectional_sync"}`，无条件放行 | 「同步是否闭环」代码侧无法否证，放行它不削弱门禁（见下）；但拦它就会把「代码侧无证据 + Jev 低置信猜疑」升级成硬违规 |
| **代码侧可否证的标签** | `awaiting_bidirectional_sync` 被当作可否证 | 明确划分为「代码侧无法否证」一类，与 `has_violation` 同列 | 代码侧只能否证「有卡级未完成事项却判空闲」及反向「无待核验卡却判等待核验」；其余三个标签约束不变 |
| **门禁拦截能力** | 依赖 cross_check 兜同步类矛盾 | 依赖 `sync_complete` noul 门禁 + compliance 档位闸 | 真实未闭环场景（卡已合入但 design 回链没写）会由 `sync_complete` 概率明确越界 → `detect_violation` 硬拦，或 compliance 落到「有关键环节缺失或存疑」低于 0.70 阈值被拦；两道闸与本条修复无关，仍独立生效 |
