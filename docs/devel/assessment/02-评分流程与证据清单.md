## 2. 评分流程（六步）

1. **快照锚定与被评对象声明**：记录 git HEAD、工作区与环境事实（§1）；由发起人指定本轮被评 Agent/模型身份，并判定与评分工具的同源关系（触发 01 §1 条款）。
2. **证据采集**：执行最小复跑包 + 静态抽查 + 文档交叉核对；可派子代理并行，但报告必须披露采样深度。
3. **对抗评审**：对评分标准（及评分草稿）执行攻击轮，处置记录留档于 01 §5。
4. **逐检查点打分**：按 01 §4 判据，证据强制，0.5 分粒度。
5. **门槛与汇总**：应用 B3 门槛、分级封顶、总评公式（01 §2）。
6. **落档与披露**：产出评分报告（03），含利益冲突与归因披露。

## 4. 复核规则

- **抽查最低要求**：B1 每线 ≥3 张卡或全量 DoD 审计（本轮为全量审计）；A2/A3 每线抽样 ≥2 个文件/域。
- **采样深度披露**：静态质量抽查为抽样而非穷尽（每线约 5–8 个文件深读），结论受采样限制，已在 03 §5 声明。
- **冲突处理**：文档声明与实测不一致 → 以实测为准，失实单点计入 C3（report 类计 C4），不重复扣分。
- **环境受限项**：统一适用封顶 75%（本轮仅 E-19 E2E 一项）。
- **归因存疑**：单发提交与时序异常（E-01/E-27）的执行者无法确认是 Agent 还是用户，照判但披露（03 §4）。

## 5. 与任务体系及归档的关系

本目录（assessment/）独立于 T 任务体系：不占用任务 ID，不触发"任务卡头部 + 总览 §4"两处同步义务，评分报告不反向修改任务卡。后续评估轮次复用 01/02，仅新增 `NN-评分报告-<轮次>.md`。

**归档边界**：打版本 tag 归档时，仅将该版本的具体评分报告（`NN-评分报告[-轮次].md`）归档至 `docs/archive/<版本号>/assessment/`，评分标准（01）与评估流程（02）常驻本目录，作为跨版本通用的活规则体系持续演进，不予归档。
