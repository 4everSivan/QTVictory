## 1. 文档体系架构

QTVictory 文档库按照**职责受众分离**原则划分为开发文档与使用指南两大分支：

```
docs/
├── README.md           # 本文档（文档中心顶层总览、全局导航与编写规范）
├── devel/              # 【开发者文档】面向系统架构、开发排期、任务卡、验收与变更核验
│   ├── README.md       # devel 子目录总索引
│   ├── design/         # 现行系统设计规范（事实源 Source of Truth）
│   ├── change/         # 变更与人工核验卡（Bug 修复与功能回调流）
│   ├── plan/           # 开发计划总览与 M1–M16 里程碑
│   ├── task/           # T01–T22 模块执行与验收卡
│   ├── report/         # M8 / M16 阶段终验报告
│   ├── env/            # 开发环境依赖盘点与磁盘清理指南
│   └── assessment/     # AI Agent 研发质量评估与证据体系
│
└── guide/              # 【用户与运维指南】面向使用者与部署运维（规划中）
    ├── README.md       # guide 子目录索引
    ├── deploy.md       # 本机单实例部署与环境变量配置
    └── user-manual.md  # 观察员控制台操作与策略计划配置指引
```

## 3. 文档命名与头部元数据规范

为确保文档**既方便人类审查者直观核对，又便于 AI/自动化脚本高精度正则提取**，全库文档必须严格遵循本节制定的命名与头部元数据格式契约。

### 3.1 格式契约（人机协同解析基础）

1. **载体**：强制采用 Markdown 引用块（`> `），位于一级标题（`# 标题`）正下方。
2. **标点与键值格式**：
   - 键名加粗，键值之间**强制采用半角冒号加单个空格**：`**键名**: 键值`；
   - 同一行内多个键值对之间**统一采用带前后空格的全角竖线分隔**：` ｜ `。
3. **状态枚举严格受控（禁止小尾巴）**：
   - 状态字段值必须严格属于受控枚举集合；
   - **严禁在状态后添加自然语言括号说明**（例如：禁止出现 `已完成（后端收口）`、`已完成(2026-09-17)`；必须纯净为 `已完成`）；
   - 如有特殊说明（如受限原因、收口注记），必须单独列于正文或专用说明行。
4. **日期格式**：所有日期必须遵循标准 ISO 格式 `YYYY-MM-DD`。
5. **文档 ID 规范**：使用**极简字母前缀法**，不采用冗长下划线单词，确保简洁且全局唯一。
6. **信息下沉原则（头部瘦身）**：
   - 活文档属于系统公有资产，不标注个人/Agent 设计责任人；
   - 详细的“影响范围”与多行“证据快照”一律下沉至正文专门章节，不在头部堆叠造成阅读堵塞。
7. **锚点纪律（防断链）**：跨文档引用章节号（如 `02 §6.1`）时——
   - 章节号只增不插中间；新增小节一律追加至同级末节之后；
   - 废弃章节原位保留并在标题标注 `[已废弃]`，编号不复用；
   - 变更卡与索引表引用设计稿时，优先“文档 + 版本 + 节号”三元组（例：`02 v3.0 §6.1`）。

### 3.2 各功能目录规范细则

#### ① 系统设计规范 (`docs/devel/design/`) —— 活文档模型
- **文件命名**: `两位数字-模块中文名.md`（例：`01-前端设计方案.md`、`02-后端设计方案.md`）
- **文档 ID**: `DESIGN-[FE/BE/CORE/...]`
- **状态枚举**: `现行基线` ｜ `讨论中` ｜ `已废弃`
- **头部模板**:
```markdown
# [方案名称]

> **文档ID**: DESIGN-[模块] ｜ **版本**: v[X.Y] ｜ **状态**: [现行基线/讨论中/已废弃]
> **最后更新**: YYYY-MM-DD ｜ **关联变更**: [C编号或无]
```
- **关联变更回填**：对应变更卡核验通过后，将 C 编号追加至头部“关联变更”字段（多个以顿号分隔；无变更保持 `无`），并在文末变更记录条目回链该卡。

#### ② 变更与核验卡 (`docs/devel/change/`) —— 变更补丁模型
- **文件命名**: `C三位编号-简述.md`（例：`C001-修复集合竞价撤单拦截.md`）
- **卡片 ID**: `C[001~999]`
- **类型枚举**: `BugFix` ｜ `Rollback` ｜ `Refactor` ｜ `Param`
- **状态枚举**: `待核验` ｜ `核验通过` ｜ `核验驳回`
- **说明**: 影响范围、受影响文件与 Checklist 一律在正文各节详述。
- **头部模板**:
```markdown
# C[三位编号] - [变更简述]

> **卡片ID**: C[001~999] ｜ **类型**: [BugFix/Rollback/Refactor/Param] ｜ **状态**: [待核验/核验通过/核验驳回]
> **创建日期**: YYYY-MM-DD ｜ **关联设计**: [设计章节链接]
```

#### ③ 开发计划总览与里程碑 (`docs/devel/plan/`) —— 里程碑跟踪模型
- **文件命名**:
  - 总览计划: `00-总体开发计划.md`、`00-前端开发计划.md`
  - 里程碑: `M[编号]-[里程碑名].md`（例：`M1-工程骨架.md`、`M16-联调验收与收口.md`）
- **ID 规范**: `PLAN-[00/FE]` 或 `M[1~99]`
- **状态枚举**: `未开始` ｜ `进行中` ｜ `已完成` ｜ `已冻结`
- **头部模板 (总览)**:
```markdown
# [计划名称]

> **文档ID**: PLAN-[编号] ｜ **版本**: v[X.Y] ｜ **状态**: [未开始/进行中/已完成/已冻结]
> **设计依据**: [设计文档链接] ｜ **最后更新**: YYYY-MM-DD
```
- **头部模板 (里程碑)**:
```markdown
# [里程碑名称]

> **里程碑ID**: M[编号] ｜ **状态**: [未开始/进行中/已完成/已冻结] ｜ **最后更新**: YYYY-MM-DD
> **上游**: [上游链接或无] ｜ **下游**: [下游链接或收口]
> **所辖任务**: [T01链接], [T02链接] ｜ **设计依据**: [设计章节链接]
```

#### ④ 任务细化规格卡 (`docs/devel/task/`) —— 执行卡片模型
- **文件命名**: `T两位数字-任务名称.md`（例：`T01-工程骨架与配置.md`）
- **任务 ID**: `T[01~99]`
- **状态枚举**: `未开始` ｜ `进行中` ｜ `已完成` ｜ `已冻结`
- **头部模板**:
```markdown
# [任务名称]

> **任务ID**: T[两位编号] ｜ **所属里程碑**: [M编号链接] ｜ **状态**: [未开始/进行中/已完成/已冻结]
> **前置依赖**: [前置任务链接或无] ｜ **后置下游**: [后置任务链接或收口]
> **设计依据**: [设计方案章节链接] ｜ **最后更新**: YYYY-MM-DD
```

#### ⑤ 验收与评估报告 (`docs/devel/report/` & `docs/devel/assessment/`) —— 审计快照模型
- **文件命名**:
  - 验收报告: `两位数字-M[编号]-验收报告.md`（例：`01-M8-验收报告.md`、`02-M16-前端验收报告.md`）
  - 评估报告: `两位数字-名称.md`（例：`01-评分标准.md`、`03-评分报告.md`）
- **报告 ID**: `R-M[编号]`、`R-ASSESS-[编号]`
- **结论枚举**: `通过` ｜ `受限通过` ｜ `未通过`
- **说明**: 机器证据快照与环境配置在正文“测试环境与证据快照”小节详述。
- **头部模板**:
```markdown
# [验收/评估报告名称]

> **报告ID**: R-[阶段编号] ｜ **版本**: v[X.Y] ｜ **结论**: [通过/受限通过/未通过]
> **验收对象**: [任务/模块描述] ｜ **验收依据**: [设计方案/评分标准链接]

```

#### ⑥ 环境治理指南 (`docs/devel/env/`) —— 环境工具模型
- **文件命名**: `两位数字-主题.md`（例：`01-环境缓存与依赖清理指南.md`）
- **文档 ID**: `ENV-[两位编号]`
- **状态枚举**: `现行有效` ｜ `已废弃`
- **头部模板**:
```markdown
# [环境指南名称]

> **文档ID**: ENV-[两位编号] ｜ **版本**: v[X.Y] ｜ **状态**: [现行有效/已废弃]

```

#### ⑦ 使用与部署运维 (`docs/guide/` 规划中) —— 用户手册模型
- **文件命名**: `纯英文短横线.md`（例：`deploy.md`、`user-manual.md`）
- **文档 ID**: `GUIDE-[模块]`
- **状态枚举**: `正式发布` ｜ `实验特性` ｜ `已废弃`
- **头部模板**:
```markdown
# [指南名称]

> **文档ID**: GUIDE-[模块] ｜ **版本**: v[X.Y] ｜ **状态**: [正式发布/实验特性/已废弃]
> **适用角色**: [量化开发者 / 观察员 / 运维人员] ｜ **最后更新**: YYYY-MM-DD
```

#### ⑧ 方向登记清单（`docs/devel/TODO.md`）—— 豁免说明
- `TODO.md` 游离于上述六类模型之外，仅需保留 `> 用途 ｜ 最后更新` 简头，不纳入元数据契约；
- **职责边界**：仅登记方向级（非缺陷）事项；Bug 修复与功能回调不入 TODO，直接在 [change/](devel/change/README.md) 建变更卡（plan/task 已随 Phase 1 封存，维护期不再经其立项）。

### 3.3 版本与变更同步规则

一次核验通过的变更卡（C 编号）必须完成以下四处同步，缺一即闭环断裂：

| 同步点 | 规则 |
|---|---|
| **design/ 对应章节** | 修订正文使全文自洽；文末变更记录增补条目并回链 C 编号 |
| **design/ 头部"关联变更"** | 追加 C 编号（多个以顿号分隔；无变更保持 `无`） |
| **design/ 版本号** | 纯勘误/措辞/格式修订 `+0.1`（如 v2.1→v2.2）；业务规则、接口契约、行为语义变更 `+1.0`（如 v2.1→v3.0） |
| **CHANGELOG.md（项目版本，semver）** | BugFix 与纯内部调整 → **PATCH**；Rollback/Refactor/Param 改动对外契约（API/错误码/行为语义）→ **MINOR**；破坏性契约变更 → **MAJOR**（1.0 前按 MINOR 计） |

**Git 锚点**：每次 CHANGELOG 版本条目合入主干时打对应 `vX.Y.Z` tag，作为验收报告与评估快照的可回取基准。
