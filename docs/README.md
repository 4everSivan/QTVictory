## 1. 文档体系架构

QTVictory 文档库按照**职责受众分离**原则划分为开发文档与使用指南两大分支：

```
docs/
├── README.md           # 本文档（文档中心顶层总览、全局导航与编写规范）
├── devel/              # 【开发者文档】面向系统架构、开发排期、任务卡、验收与变更核验
│   ├── README.md       # devel 子目录总索引
│   ├── design/         # 现行系统设计规范（事实源 Source of Truth）
│   ├── change/         # 变更与人工核验卡（Bug 修复与功能回调流）
│   ├── plan/           # 开发计划总览与 M1–M16 里程碑
│   ├── task/           # T01–T22 模块执行与验收卡
│   ├── report/         # M8 / M16 阶段终验报告
│   ├── env/            # 开发环境依赖盘点与磁盘清理指南
│   ├── assessment/     # AI Agent 研发质量评估与证据体系
│   └── todo/           # 待办与需求缓冲池（按版本分文件登记，落地即移出）
│
└── guide/              # 【用户与运维指南】面向使用者与部署运维
    ├── README.md       # guide 子目录索引
    ├── 01-单机部署与运维指南.md # 本机单实例部署与环境变量配置
    ├── 02-测试环境部署指南.md   # local/ 集中隔离与测试环境部署规范
    └── 03-观察员控制台操作指南.md # 观察员控制台操作与策略计划配置指引（规划中）
```

## 3. 文档命名与头部元数据规范

为确保文档**既方便人类审查者直观核对，又便于 AI/自动化脚本高精度正则提取**，全库文档必须严格遵循本节制定的命名与头部元数据格式契约。

### 3.1 格式契约（人机协同解析基础）

1. **载体**：强制采用 Markdown 引用块（`> `），位于一级标题（`# 标题`）正下方。
2. **标点与键值格式**：
   - 键名加粗，键值之间**强制采用半角冒号加单个空格**：`**键名**: 键值`；
   - 同一行内多个键值对之间**统一采用带前后空格的全角竖线分隔**：` ｜ `。
3. **状态枚举严格受控（禁止小尾巴）**：
   - 状态字段值必须严格属于受控枚举集合；
   - **严禁在状态后添加自然语言括号说明**（例如：禁止出现 `已完成（后端收口）`、`已完成(2026-09-17)`；必须纯净为 `已完成`）；
   - 如有特殊说明（如受限原因、收口注记），必须单独列于正文或专用说明行。
4. **日期格式**：所有日期必须遵循标准 ISO 格式 `YYYY-MM-DD`。
5. **文档 ID 规范**：使用**极简字母前缀法**，不采用冗长下划线单词，确保简洁且全局唯一。
6. **信息下沉原则（头部瘦身）**：
   - 活文档属于系统公有资产，不标注个人/Agent 设计责任人；
   - 详细的“影响范围”与多行“证据快照”一律下沉至正文专门章节，不在头部堆叠造成阅读堵塞。
7. **锚点纪律（防断链）**：跨文档引用章节号（如 `02 §6.1`）时——
   - 章节号只增不插中间；新增小节一律追加至同级末节之后；
   - 废弃章节原位保留并在标题标注 `[已废弃]`，编号不复用；
   - 变更卡与索引表引用设计稿时，优先“文档 + 版本 + 节号”三元组（例：`02 v3.0 §6.1`）。

### 3.2 各功能目录规范细则

#### ① 系统设计规范 (`docs/devel/design/`) —— 活文档模型
- **文件命名**: `两位数字-模块中文名.md`（例：`01-前端设计方案.md`、`02-后端设计方案.md`）
- **文档 ID**: `DESIGN-[FE/BE/CORE/...]`
- **状态枚举**: `现行基线` ｜ `讨论中` ｜ `已废弃`
- **头部模板**:
```markdown
# [方案名称]

> **文档ID**: DESIGN-[模块] ｜ **版本**: v[X.Y] ｜ **状态**: [现行基线/讨论中/已废弃]
> **最后更新**: YYYY-MM-DD ｜ **关联变更**: [C编号或无]
```
- **关联变更回填**：对应变更卡核验通过后，将 C 编号追加至头部“关联变更”字段（多个以顿号分隔；无变更保持 `无`），并在文末变更记录条目回链该卡。

#### ② 变更与核验卡 (`docs/devel/change/`) —— 变更补丁模型
- **文件命名**: `C三位编号-简述.md`（例：`C001-修复集合竞价撤单拦截.md`）
- **卡片 ID**: `C[001~999]`
- **类型枚举**: `BugFix` ｜ `Rollback` ｜ `Refactor` ｜ `Param`
- **状态枚举**: `待核验` ｜ `核验通过` ｜ `核验驳回`
- **核验收尾机制**: 摒弃强制人工手签；由 AI 执行测试与实测后在对话中向人工汇报，人工在会话中确认无误后，由 AI 代为完成结论签署与归档收尾。
- **双向关联纪律**: 变更卡必须明确链接对应设计章节锚点；对应设计方案的小节原位亦必须增补反向引用标签（`> 📌 **关联变更**: [C00x]...`），形成双向互通。
- **头部模板**:
```markdown
# C[三位编号] - [变更简述]

> **卡片ID**: C[001~999] ｜ **类型**: [BugFix/Rollback/Refactor/Param] ｜ **状态**: [待核验/核验通过/核验驳回]
> **创建日期**: YYYY-MM-DD ｜ **关联设计**: [02-后端设计方案.md §3.4](devel/design/02-后端设计方案.md#34-行情服务marketservice)
```

#### ③ 开发计划总览与里程碑 (`docs/devel/plan/`) —— 里程碑跟踪模型

  - 里程碑: `M[编号]-[里程碑名].md`（例：`M1-工程骨架.md`、`M16-联调验收与收口.md`）
- **ID 规范**: `PLAN-[00/FE]` 或 `M[1~99]`

#### ⑧ 待办与需求缓冲池（`docs/devel/todo/`）—— 缓冲池模型
- **定位与契约**：`todo/` 作为项目未入轨事项的轻量缓冲池（Backlog Intake Queue），按当前版本与远期储备分设文件（[now.md](devel/todo/now.md)、[future.md](devel/todo/future.md)），支持多端/多 Agent 并行编辑，避免单一文件合并冲突；
- **表格化呈现**：所有缺陷与功能一律采用标准 Markdown 表格记录，明确 ID、模块、描述、优先级/严重度、登记日期与流转目标；
- **落地即移出（零沉淀纪律）**：只要事项落入 [change/](devel/change/README.md)（创建 C 卡）或 [design/](devel/design/README.md)（更新设计基线），**必须立即从 todo 表格中物理删除**；`todo/` 坚决不保留 `[x]` 历史勾选项，闭环与审计由 change/design 全权承载。
- **编号与度量口径**：前缀语义（BG/EN/FT/TD）+ 四位序号只增不复用、严重度 S1–S4 与优先级 P0–P3 受控枚举、版本文件生命周期与标准表模板，详见 [todo/README.md](devel/todo/README.md) §2–§5。

### 3.3 版本与变更双向同步规则

一次核验通过的变更卡（C 编号）必须完成以下全链路双向同步，缺一即闭环断裂：

| 同步点 | 双向闭环规则 |
|---|---|
| **design/ 对应章节原位** | 修订正文保持全文自洽；在被关联小节原位增补反向引用标签（`> 📌 **关联变更**: [C00x]...`），使读者能从设计章节直接跳转查阅补丁卡 |
| **design/ 头部与文末记录** | 头部“关联变更”追加 C 编号（多个以顿号分隔）；文末变更记录增补条目并双向回链 C 卡 |
| **design/ 版本号** | 纯勘误/措辞/格式修订 `+0.1`（如 v2.1→v2.2）；业务规则、接口契约、行为语义变更 `+1.0`（如 v2.1→v3.0） |
| **CHANGELOG.md（项目版本）** | 按 semver 记账（BugFix/内部调整→PATCH；契约调整→MINOR；破坏性变更→MAJOR）；条目必须带 `[C00x]` 形式超链接（例：[C001](devel/change/C001-修复日K引导入库元组缺code.md)） |
| **C00x 变更卡收尾归档** | AI 汇报实测并在会话中与人工对齐；人工确认后由 AI 代签收尾（记录会话确认要点与纳入版本号），杜绝人工手写负担 |

**Git 锚点**：每次 CHANGELOG 版本条目合入主干时打对应 `vX.Y.Z` tag，作为验收报告与评估快照的可回取基准。
